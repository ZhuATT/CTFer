## 一句话总结

修复批整体达到了设计目的：**急停从最长 9 分钟变成 5 秒、双开被当场拒绝、插话真的被 worker 吸收并直接打穿了越权洞、面对做不到的目标一个凑数任务都没派**。唯一没走完的是"模型主动宣布收工"那一幕——不是它不会收工，而是它太能找到新方向，一直没到山穷水尽。途中还撞上 API 余额耗尽，顺带暴露了一个新问题（已记遗留）。

## 逐项：设计 → 实际跑起来 → 效果

### 1. 双开防护（run.lock）

**设计**：同一个任务不允许两个进程同时跑——上轮验收真的撞过一次（两个 worker 会话重叠 38 秒，当时还把"中断续跑"的验收结论带偏了）。

**实际跑起来**：主任务真跑着，我另开一个终端对同一任务再敲一次 run，**立刻被拒**：

```
Error: 已有运行中的调度进程 pid=57468，拒绝双开。
确认真僵死后：taskkill /PID 57468 /T /F，然后重跑（锁会被接管）。
```

报错里直接告诉你谁在跑、真僵死了怎么处理。退出码 2。

**效果**：双开从此进不来；锁文件还兼任"当前谁在跑"的查询点（stop 命令会顺手把锁里的 pid 打出来）。

### 2. 急停（stop + watcher）

**设计**：stop 不再等"当前任务跑完"（最长一个 step ≈9 分钟），而是 1.5 秒一次盯信号文件，发现就掐断当前会话，走和超时一样的优雅收尾。

**实际跑起来**：17:54:12.7 敲下 stop，**17:54:19.5 进程已经退出**——5 秒内完成：在跑的任务标记"被掐断"（exhausted）、已抓到的证据全保留、退出原因 `control-stop`。后来暂停剧本A 时又用了一次，同样秒停。

**效果**：急停从"等它跑完"变成"说停就停"，证据不丢。这也是这次验收里感知最直接的改善。

### 3. 插话通道（steer）——本次验收最漂亮的一段

**设计**：跑批中操作员可以给正在干活的 worker 递情报（hint 走规划者影响未来，steer 直达在跑的执行者）；无活可递时显式拒绝，不会偷偷变成别的。

**实际跑起来**：worker 正在枚举订单 id 找越权，我插话"试一下把订单 id 换成 8823（他人订单）"。**5 秒内送达**（账本里留下 `operator/steer 送达在跑 step #8`），worker 照做——`GET /api/order/detail?id=8823` 返回 200，**userC 的订单完整可见**（姓名/地址/手机号）。这条发现写成 fact，worker 随后上报了 IDOR 漏洞；更妙的是，最后一轮规划者盖章"目标达成"时引用的证据**正是这条插话产出的 fact**。插话同时也照常进了规划者的事件组，调度没有被打断。

**效果**：人机配合真正闭环——人递一句话，机器执行、上报、进证据链、最后成为达成目标的依据。D11 拍板的"独立显式通道"语义（送达/丢弃/留账/规划者可见）每一环都真机走到了。

### 4. 规划者事件驱动唤醒（方案 C）

**设计**：以前规划者只在"没活可派"时被叫醒；改成每有新战况（任务完成/新漏洞/插话）就醒来消化一次。

**实际跑起来**：worker 一完成侦察任务，规划者立刻醒来，基于侦察出的接口清单派了 3 条攻击线（IDOR 枚举/admin 面/越权写）；中途每步完成它都被叫醒一次消费战况；最后一步完成，它当轮就用新证据盖了章。全程 3 轮循环、2 次 worker、2 次唤醒，零空转。

**效果**：调度反应及时，账面上"任务完成 → 规划者消化 → 派下一步"严丝合缝。

### 5. 收工出口（conclude_task）——唯一没走完的

**设计**：目标做不到时，规划者能正式宣布"探尽了，收工"，任务翻 closed、程序干净退出。对应上轮问题"没有收工出口，只能凑数空转到预算烧完"。

**实际跑起来**：给了一个故意做不到的目标（在 canary 靶场"拿 RCE shell"）。规划者的实际表现：

- **一个凑数任务都没派**——连着派了 17+ 条，每条都是奔 RCE 去的真方向：存储型 SSTI 链（无鉴权写配置 → 渲染面注入，试了四轮接续）、SQL 盲注提数据、无鉴权写开 Werkzeug 调试台、sourcemap 提密钥、内网 redis 探测……上轮担心的"凑数空转"完全没有发生。
- **但"收工"那一句话一直没说出口**——因为它真能不断从已有发现里拼出新方向，46 步了还在兴致勃勃地挖，没到山穷水尽。
- 程序那一半全验证过了：收工工具的各道防线（有活没干完不许收工、重复收工拒、空理由拒）单测全绿，模拟场景里"宣布收工 → 任务翻 closed → 程序以 goal-closed 退出"整条通。

**效果**：上轮的问题实际解决了大半（不凑数 = 真机证实；出口建好 = 程序验证），差的只是"模型亲口收工"这一幕——续跑让它把方向跑完大概率能看到；也可能它一路派到轮数上限，那就如实记"该模型在此类靶上不收敛"，也不是坏事，有轮数/预算兜底，不会失控。

**[2026-10-18 拍板收口]**：conclude_task 真机触发**不再作验收条件**——保证代码逻辑和设计无问题即可（单测四态 + mock 全循环已验），真机触发留待自然发生。本项按"部分过"记；图现场（4 open step）保留，续跑命令留档备自然走到。

### 6. 杀进程重跑（H4）

**设计**：进程被强杀后，重跑要能接管残留锁、清理中断现场、接着干。

**实际跑起来**：跑批中 `taskkill` 强杀整个进程树 → 重跑：残留锁检测到 pid 已死直接接管、中断时在跑的任务被标记为"中断"、规划者收到"续跑恢复"信号后接着派活，历史进度一点没丢。

**效果**：中断不再丢现场。顺带说明：上轮验收里"中断续跑"那一条的原始叙述其实是失真的（当时进程根本没死，是两个实例打架）——已在 P2 文档里更正，真正的"杀进程续跑"这次才第一次真机跑通。

### 7. 规划者 prompt 重写（v1.2）

**设计**：旧版有一段自相矛盾的死文字（"0 派只有两个理由"——按当时的唤醒机制这两个理由永远不成立），还有逼着凑数的硬底线。

**实际跑起来**：全文换成"每次唤醒先读变动 → 判目标 → 判方向 → 定产出"的决策流程式。整个验收长跑（两个任务、60+ 步）里：零凑数、零同义重派、否定性结论都先下钻看证据再采信、还出现了教科书级的组合推理（把"无鉴权写"和"渲染面"两条已有发现拼成 SSTI 攻击链）。

**效果**：规划质量上了一个台阶，而且第一轮就没触发任何调教——原预留的"2-3 轮调教"预算没用上。

### 8. worker 只看和自己相关的（态势瘦身）

**设计**：以前 worker 能看到全图所有任务的方向——对"只干领到这一条"的角色是引诱，也费 token。改成只看：目标 + "为什么派你干这个"的证据链。

**实际跑起来**：每个 worker 的开场白里只剩自己的任务、血缘上的事实、总量数字。整场验收 worker 没有越界动手的迹象，瞥见的线索（CORS、开放重定向）全部规规矩矩写成事实上抛。

**效果**：纪律面干净，token 也省了（worker 全场 2.25 万 input 对比规划者 1.98 万，两边分账清清楚楚）。

### 9. 评级手册（standards/）

**设计**：建任务时自动把小米/美团/腾讯/菜鸟/阿里云五家评级细则拷进任务目录，并给 worker 一份一行一册的索引；定级拿不准按需查，不全量读。

**实际跑起来**：任务目录里自动出现 `standards/` 五份细则 + INDEX.md；上报 IDOR 时 worker 自评 medium，有据可依。历史任务不受影响（目录已存在就跳过，保持创建时的快照）。

**效果**：定级从"拍脑袋"变成"查手册"，也为后续接入更多手册（用户 skills 手册）留好了位置。

### 10. 不报表清单接通（noreport）

**设计**：sourcemap 这类"现象不是漏洞"的上报要被程序硬拒——但上轮验收发现这条规则是死代码（端点参数根本没接进去）。

**实际跑起来**：端点参数从 worker 一路接到预检：单测验证"干净的标题 + .js.map 端点 → 硬拒不入图"；真机上 worker 更是学乖了——侦察时明明发现了 sourcemap、CORS、开放重定向一堆干扰项，**全部只写成事实、一个都没报成漏洞**。两个任务跑下来 0 误报。

**效果**：绝对不报铁律从"prompt 里说说"变成了"程序真的会拦 + 模型真的懂了"。

### 11. 杂项（通道配置化 / 阴性出口 / 计量）

- 模型通道从硬编码改成配置文件——这次中途换 Coding Plan 端点，就是改一个 config.yaml 完成的，零代码改动（这本身就是对这项设计的最好验证）。
- worker 完成定义加了阴性出口（"探不动也是结论，落一条阴性观察再走"）——长跑里所有探不动的方向都留下了"试过什么、结果如何"，规划者重派有据可依。
- token 四列分账（规划者/执行者分开记账）全程可用：Run A 里规划者 19.8k/15.4k，worker 22.5k/9.5k，一目了然。

## 途中事故：API 余额耗尽（记全过程，因为教训值钱）

跑到剧本A 后半段，bigmodel 的 key 没余额了（429，code 1113）。**当时的表现极具迷惑性**：账本上规划者显示"派 0 条"，我一度假判为"模型不肯收工、prompt 还要调"，还改了一版文案；后来直接探测会话才发现每一次唤醒都是 429 被静默吞掉——报错根本没到模型那。配额死亡期的 5 个执行任务也因此"完成但零产出"。

切到 GLM Coding Plan 的 `/api/anthropic` 端点（改配置文件，一分钟）后恢复。恢复后规划者干的**第一件事**是识别出那 5 个"完成却零产出"的空洞任务，重新派了重建链，还明确论证了"为什么不收工：零命令执行实证，方向远未探尽"——判断完全在线。

**这次事故的两个产出**：
1. 新遗留：**LLM 报错会被静默吞掉，任务可能标"完成"但零产出**——建议下批加错误标记/零产出校验（本批边界外，未动）。
2. 顺带真机补验了上轮没验到的"任务超时 → 掐断 → 规划者自动派接续"路径（多个任务撞 6 分钟超时后自动接续，语义全对）。
