## F1 `--rounds` 语义事故：绝对轮号当相对轮数用

### 什么原因

`run --rounds N` 把 N 传给 `Stoploss(max_rounds=N)`，每轮末判定 `rnd >= max_rounds` 即停（stoploss.py）。问题在 `rnd` 的含义：**S5 设计让它从簿记续号（跨 run 持久的绝对轮号）**——老 engagement 第 6 次启动时 rnd 一上来就是 6，不是从 1 数。

这条判定写下时（批3 之前）默认场景是全新 engagement 从 0 起跑，绝对=相对，没人分得出区别；批4fix S5 引入持久轮号后两者分家，**判定没跟着改**——绝对比较的语义就这么留了下来。

### 带来什么后果

- **10-12 实抓**：E5a/E5b 两个补充实验在轮号=5 的 engagement 上跑 `--rounds 1`，启动即停（`stoploss(B):会话上限：第 5 轮 ≥ 1`）——我的意图是"再跑 1 轮"，系统的理解是"轮号到 1 就停"，而轮号已经是 5，所以一秒没跑就收工。实验被迫换路径完成，多烧了两次 run 启动成本。
- **对日常使用**：任何"给老 engagement 补 N 轮"的操作**必踩**（补一轮、加跑两轮都是正常操作场景，不是边角）。踩了不崩，但 run 被静默秒停，不看日志还以为跑完了。
- **附带**：`stoploss_trigger` 事件文案"会话上限：第 5 轮 ≥ 1"同样基于绝对语义，人读了一样误解。

### 修复计划

- run 启动时记 `base_round`（本次 run 启动时的簿记轮号），判定改为 `(rnd - base_round) >= max_rounds`。
- 落点推荐：`Stoploss` 构造加 `base_round` 参数，差值在 should_stop 内算——改动集中一处，driver 只多传一个数。（备选：driver 直接传 `max_rounds=base+N`，代码最少但语义藏得深，后人看不懂，不取。）
- 连带：`stoploss_trigger` 事件文案改"本次 run 轮数上限：已 N/M 轮"。
- 用例：①续跑 engagement（簿记轮号=5）+ `--rounds 1` → 恰好多跑 1 轮；②存量回归：全新 engagement 的 `--rounds N` 行为不变（现有 test_driver max_rounds 用例保持绿）。

## F2 resume 事件误发：播种发生在判定之前

### 什么原因

`resume` 事件的本意是"这是老 engagement 续跑"，判定条件是"启动时图非空"（driver.py：`if bb.graph["nodes"]: ev.emit("resume", ...)`）。

但主流程的顺序是：**先**跑配方 0 播种（`_seed_from_engagement` 往图里种一条目标画像 fact，图从 0 变 1）→ **再**发 run_start 和 resume 判定。顺序一反，新 engagement 首跑时图必然非空——判定永远为真。

### 带来什么后果

- **10-12 实抓**：jwzx 主战和陪跑的首跑，auto-log 里各有一条假的 `resume {nodes:1}`——第一轮就写着"续跑"。
- **影响范围**：纯日志误导，**无功能后果**——没有任何逻辑消费 resume 事件（真正驱动续跑行为的是 phase.json 残留，另一条线），它只服务于人看回放/审计。但误导是实打实的：回放时会以为这个 engagement 中途重启过。
- 比喻：新员工入职第一天，考勤系统看到工位上已经有个牌子（HR 提前放的欢迎牌），记了一笔"老员工返岗"。

### 修复计划

- 判定加一个条件：**簿记轮号 > 0**（轮号跨 run 持久，新 engagement 必为 0，真续跑必有轮号）：
  `if bb.graph["nodes"]:` → `if int(bb.bookkeeping.get("round", 0) or 0) > 0 and bb.graph["nodes"]:`
- 一行改动。真续跑（轮号≥1 且图非空）不受影响，种子画像照种。
- 用例：①全新 engagement 首跑 → 无 resume 事件；②第二次 run → 有 resume 事件。

## F3 skills 供给遗漏：建 engagement 时三条注入途径一条没走

### 什么原因

skills 进 worker 有三条途径（优先级：engagement.json 的 `skills_src` > 环境变量 `AT1_SKILLS_SRC` > 无）——这条供给链的**代码是通的**（cwcx 实机验证过、`test_skills_src_env_fallback` 在跑）。10-12 建 jwzx 两个 engagement 时，我**三条全没走**：engagement.json 没写 skills_src 字段、shell 没export、也没手动放目录（已当场查实：`.claude/skills` 不存在）。

纯 setup 遗漏，不是代码 bug——但暴露了一个流程缺陷：**供给靠人记，没有默认值兜底**，忘了就是静默裸奔（系统不警告"这个 engagement 没带 skill 库"）。

### 带来什么后果

- jwzx 6 轮 worker **全程裸奔**：26 个攻击 skill（注入/越权/SSRF 方法论与 payload 库）一个没进 `.claude/skills/`，worker 遇到攻击信号时没有 skill 路由可查，方法论全靠模型自带。
- 实际产出没有肉眼可见的下降（系统化阴性排除、GUID 计数器结构分析都做出来了）——但这**不能反推 skills 没用**：可能这个靶（老式 JSP 教务系统，攻击面朴素）恰好不需要，换现代靶（API/加密/复杂前端）可能就是另一个故事。"skills 的边际价值"从设计假设变成了未量化问题。
- 对验收本身：不影响 17/17 结论（验收的是平台机制，不是攻击质量）。

### 修复计划

- `.secrets.env` 加一行：`AT1_SKILLS_SRC=D:/Downloads/hacker/.claude/skills`——每次 run 都 source 这个文件，**以后建 engagement 不用再想这件事**，忘了 engagement.json 字段也有全局默认兜底。
- 不改代码（优先级链已实现、已测试）。
- 验证：下个 engagement 展开后 `.claude/skills/` 在场（expand 时复制，一眼可查）。
- 量化（本批不做，记入边界）：下个靶对照跑一轮（一个带 skills 一个不带），拿 findings/facts 产出密度对比。

## F4 文档措辞失实：两处历史乐观表述

### 什么原因 / 带来什么后果

| 措辞 | 为什么失实 | 误导后果 |
|---|---|---|
| **"环境消毒"**（worker 拿不到控制器内部状态） | B3 白名单放行 `PLAYWRIGHT_MCP_CDP_ENDPOINT` 后，worker 能看到浏览器附着端口——控制器内部状态被有意共享 | 读者以为 worker 环境是全隔离的；威胁模型误判。实际影响 ≈ 0（worker 本就有完整浏览器操作权限，没新增能力，2026-10-13 用户拍板），但措辞必须跟事实对齐 |
| **guard"拦截"**（拦下/照拦） | guard 挂在工具**结果回调**上，命令执行完才扫描记录——从来不阻断。P-9 拍板它就是"摄像头" | 读者以为 guard 会挡危险操作；实际 worker 跑 `rm -rf` 也拦不住，只能事后记账。如果有人基于"有 guard 挡着"放松对 worker 命令的审视，就是真风险 |

两处都是文字写在前、事实发生在后（B3 放行/实抓只拍不拦），没人回头改字。

### 修复计划

- 措辞①改写为：「消毒防的是**凭证与控制器变量误传**（AT1_*/LLM_*/API key）；浏览器附着通道是**有意共享**（worker 的正当工具）；威胁模型 = worker 可全权操作本 engagement 浏览器（同信任域，2026-10-13 拍板接受）」。落点：`playwright升级计划.md` §3-B3 注记；`at1-执行开发计划.md` §3.1 有对应措辞一并改。
- 措辞②：guard 语境下所有"拦"改"记录"（`v3批4fix实机测试计划.md` §6 B2 行、guard 相关注释与文档）。
