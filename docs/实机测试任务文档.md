## 7. 修复登记（实跑发现，先记录不动手——2026-11-08 首跑现场）

### R-1 🔴 planner 优先级语义颠倒 → 开局单系统性饿死【已修 ✅（2026-11-09 施工：A+B+C 全案=`33243c4` 卡1 R1-A 语义钉死 + 卡2 R1-B 态势感知 + `0f53b6c` 卡3 R1-C 调度 aging；见 `首跑修复批-施工计划.md`）】

- **现象**：给定账号登录 step#5 开局创建、全程 open 未执行；执行序列 #2→#10→#15→#21→#34 与各单 priority 严格吻合 `priority DESC`。planner 叙述始终把 #5/#3/#4 称为"在跑/在途/五线并存"——**其系统模型与真实队列脱节**，并在 #199 明言"等 step#5 fact 回来即派越权线"（等一个永远不会来的产出）。
- **根因**（两层叠加）：
  1. **语义错配**：`scheduler.ts:74` nextStep=`ORDER BY priority DESC, id ASC`（注释"高价值链路优先"，数值大=先跑）；planner prompt **从未教过这个语义**，开局按 P1/P2 习惯给它认为最重要的 #3 标了 **1**（数值垫底）、#4/#5 标 2。中途派单自改 3/4 递增恰好对齐调度器——唯开局批反标。executor 序列证明调度器无恙，纯 planner 标注问题；
  2. **无 aging/重估机制**：老 open 单无"开单 N 轮未执行强制重估"，新单只要 priority ≥ 旧单就永久插队；planner 态势里也无"此单已开未跑 X 轮"字段，它无从察觉饿死。
- **证据**：activity #199（派0条+等 #5 的矛盾决策）；nodes 表 priority 值（#3=1/#4=2/#5=2/#10·15·21=3/#34=4）；`scheduler.ts:71-74`。
- **修法候选**（2026-11-08 二读更新：A+B 已拍板，第三件讨论中）：
  - A（语义钉死，~3 行）✅ 已拍板：planner-prompt.ts 引导句 + **planner.ts:172 add_step 参数描述**（现句"0-5，高价值链路优先被领，默认 0"语义含糊，P1/P2 惯性下坑人——双落点同钉"数值大=先跑"）+ PI-prompt.md 同步 + 断言测试；

## 三、问题与新观察登记（本run暴露，详细版）

### N-1 🟡 guard 静态防线 × deepseek 命令卫生风格（3 次拦截，跨模型行为差异首次显形）

- **现象**：#289/#419/#434 三次 `blocked: destructive-command`，全部命中 `rm -f`。典型样本（#288→#290）：登录链复合命令开头挂 `rm -f evidence/cookies.txt`（清理自家 cookie 罐）→ 整条被拦 → worker 下一拍**摘掉 rm 重提即过**，后续改用新文件名罐（ck2.txt）规避删除需求——**零绕行企图，自愈一个 step 内完成**。
- **对照**：flash 首跑 76 次工具调用零拦截；deepseek 上岗 1 小时 3 次。防线本身按设计工作（静态匹配宁误拦不放行，误拦成本=一次重试），非故障。
- **暴露的次级面**：①拦截回执只有「命中 rm -f」四个字，合规路径全靠模型自己悟——悟性差的模型可能反复撞墙烧轮数；②这是"框架行为依赖模型习惯"的第一个跨模型对照样本，换通道后此类摩擦面值得持续观察。
- **【勘误 2026-11-09】**两处原判定不准：①"回执只有四个字"不成立——detail 审计字段里才是「命中 rm -f」，模型实际收到的回执是完整「平台管控·非目标防御 + 禁绕过 + 正确做法」文案；②"首跑零拦截对照"不成立——首跑 activity #94 同规则同命中（`rm -f`），续跑 #289/#419/#434 共 3 次。Bash 调用尝试数：首跑 131、续跑 137，拦截占比约 0.76% / 2.19%——**非同条件对照实验**，不能由此归因模型习惯差异。
- **讨论项**：D-a。

### N-2 ⚪ step 超时是合作式软边界（+~2min grace）

- **现象**：#62 墙钟 22min，过 20min 超时线后未立即掐断，在途工具/final message 走完后收尾，**终态 done 非 exhausted，产出零丢失**。
- **【勘误 2026-11-09】本节判定作废**：22min 是「建单→结果记账」口径，其中约 20min 为排队等待（worker 会话 05:25:20.829Z 创建，05:27:43 记账，会话内执行仅 ~2min22s）——**不构成 20min 执行超时样本**；"两分钟 grace"是把排队时间误读成收尾宽限。另：当时无 stopReason 落账，"终态 done"由旧收尾逻辑推出（空结束/无交付也判 done，11-9实机fix §5.1），不可作为"软边界保产出"的证据。本批已加 queue_wait/worker_elapsed/cleanup_elapsed 三段计时，此类误判不再复现。
- **机制**：`setTimeout(doAbort)` → `agent.abort()` 走 pi 优雅收尾路，abort 合作式（不硬杀在途流）。
- **定性**：设计内（P2F-5 优雅收尾语义）。代价=超时点不精确，收益=不丢产出。本档倾向不动（D-b）。
