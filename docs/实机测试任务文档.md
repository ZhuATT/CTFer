## 7. 修复登记（实跑发现，先记录不动手——2026-11-08 首跑现场）

> 本节登记 real-usc2 首跑暴露的框架缺陷。**状态全为"待拍板/待修"**，不影响本次验收对账；修法落地前续跑会带着已知缺陷跑（见各条"带病跑影响"评估）。

### R-1 🔴 planner 优先级语义颠倒 → 开局单系统性饿死【已修 ✅（2026-11-09 施工：A+B+C 全案=`33243c4` 卡1 R1-A 语义钉死 + 卡2 R1-B 态势感知 + `0f53b6c` 卡3 R1-C 调度 aging；见 `首跑修复批-施工计划.md`）】

- **现象**：给定账号登录 step#5 开局创建、全程 open 未执行；执行序列 #2→#10→#15→#21→#34 与各单 priority 严格吻合 `priority DESC`。planner 叙述始终把 #5/#3/#4 称为"在跑/在途/五线并存"——**其系统模型与真实队列脱节**，并在 #199 明言"等 step#5 fact 回来即派越权线"（等一个永远不会来的产出）。
- **根因**（两层叠加）：
  1. **语义错配**：`scheduler.ts:74` nextStep=`ORDER BY priority DESC, id ASC`（注释"高价值链路优先"，数值大=先跑）；planner prompt **从未教过这个语义**，开局按 P1/P2 习惯给它认为最重要的 #3 标了 **1**（数值垫底）、#4/#5 标 2。中途派单自改 3/4 递增恰好对齐调度器——唯开局批反标。executor 序列证明调度器无恙，纯 planner 标注问题；
  2. **无 aging/重估机制**：老 open 单无"开单 N 轮未执行强制重估"，新单只要 priority ≥ 旧单就永久插队；planner 态势里也无"此单已开未跑 X 轮"字段，它无从察觉饿死。
- **证据**：activity #199（派0条+等 #5 的矛盾决策）；nodes 表 priority 值（#3=1/#4=2/#5=2/#10·15·21=3/#34=4）；`scheduler.ts:71-74`。
- **修法候选**（2026-11-08 二读更新：A+B 已拍板，第三件讨论中）：
  - A（语义钉死，~3 行）✅ 已拍板：planner-prompt.ts 引导句 + **planner.ts:172 add_step 参数描述**（现句"0-5，高价值链路优先被领，默认 0"语义含糊，P1/P2 惯性下坑人——双落点同钉"数值大=先跑"）+ PI-prompt.md 同步 + 断言测试；
  - B（数据面，~10-15 行）✅ 已拍板：`graph.ts` graphOverview 的 steps 数组（现仅 `{id,summary,note,state}`，**planner 连自己标的 priority 都看不见**）加 `priority` 回显 + `open_age_min`（state=open 时 created_at 距今分钟数）；overview 整体 JSON 进 planner prompt（planner.ts:421）自动流转，字段导读补半句。直接治 P-2（"在跑"幻觉被年龄戳穿）；
  - b-1（update_step 工具）↩️ **提出后撤回**：新发现的缺口——planner 工具箱无任何调老单 priority/收单的工具，add_step 同义去重还拒收重开（planner.ts:165），B 若不配动作面=只给眼睛不给手。但补 LLM 手工调队列是弱机制：纠错者=犯错者、占唤醒、多 worker 下 planner 成队列管理员瓶颈。撤回，改提 C；
  - C（调度器硬保证）✅ **已拍板进本批（2026-11-09）**：nextStep 时间制 aging——`有效优先级 = priority + min(floor(open分钟/aging_min), cap)`，ORDER BY 有效值 DESC, id ASC（id tiebreak 本就是 FIFO）。默认 aging_min=15 / **cap=+5**（2026-11-09 复核修正：cap=3 时 P1/P0 加满也只到 4/3 摸不到顶，持续 P4+ 新单流下仍会饿死；cap 必须能追平最高档。**保证不变式：任何 open 单最长 (5−priority)×15 分钟后登上队首**——P4→15min/P3→30/P2→45/P1→60/P0→75）；created_at 落库，**续跑天然继续 aging**（比轮数制好——轮数是内存值跨 run 清零）；参数进 config.yaml run 段。多 worker 通吃：priority 队列+aging 是 1..N worker 的通用解（ARTEX 同款队列语义），无需 LLM 参与。
