### 卡3 R1-C：nextStep 时间制 aging（饿死机械保底，多 worker 通吃）✅0f53b6c

**背景**：现行 `ORDER BY priority DESC, id ASC` 下，新单分数 ≥ 老单即永久插队（首跑 #5 挂满全场）。修法=等待时间等效加成：`有效优先级 = priority + min(floor(open分钟/agingMinutesPerBoost), agingBoostCap)`。**保证不变式：任何 open 单最长 (5−priority)×agingMinutesPerBoost 分钟后登上队首**（cap=5 时）。纯 SQL 现算，无新列无迁移；created_at 落库，续跑天然继续 aging。

**落点与改动**：

1. `src/config.ts`——RunConfig 接口加两字段（含注释）：

```ts
/** R1-C：open step 等待 aging——每挂满 N 分钟 priority 等效 +1。缺省 15。 */
agingMinutesPerBoost?: number;
/** R1-C：aging 加成上限，缺省 5——任何 open 单最长 (5−priority)×agingMinutesPerBoost 分钟后登上队首。0=关闭（退回纯 priority DESC）。 */
agingBoostCap?: number;
```

DEFAULTS.run 改为 `run: { maxRounds: 20, budgetMs: 3_600_000, circuitBreaker: 3, agingMinutesPerBoost: 15, agingBoostCap: 5 }`；
loadConfig run 段照 circuitBreaker 模式加两行校验（注意 `agingBoostCap` 允许 0，条件用 `>= 0`；`agingMinutesPerBoost` 用 `> 0`）。

2. `src/scheduler.ts`——nextStep 重写（导出 AgingOptions；注释同步更新）：

```ts
/** 领下一条 step：有效优先级 = priority + aging 加成（每 minutesPerBoost 分钟 +1，封顶 boostCap；cap=0 或不传退回纯 priority DESC）。同效值 id 小（先建）先走=FIFO。
 * R1-C（首跑 R-1 饿死的机械保底层）：不依赖 planner 自觉，任何 open 单有界等待后必然上位。 */
export interface AgingOptions {
	minutesPerBoost: number;
	boostCap: number;
}

export function nextStep(db: Database, taskId: string, aging?: AgingOptions): NodeRow | undefined {
	const on = aging && aging.boostCap > 0 && aging.minutesPerBoost > 0 ? aging : undefined;
	if (!on) {
		return db
			.prepare("SELECT * FROM nodes WHERE task_id=? AND kind='step' AND state='open' ORDER BY priority DESC, id ASC LIMIT 1")
			.get(taskId) as NodeRow | undefined;
	}
	return db
		.prepare(
			"SELECT * FROM nodes WHERE task_id=? AND kind='step' AND state='open' " +
				"ORDER BY (priority + MIN(CAST((julianday('now') - julianday(created_at)) * 1440.0 / ? AS INTEGER), ?)) DESC, id ASC LIMIT 1",
		)
		.get(taskId, on.minutesPerBoost, on.boostCap) as NodeRow | undefined;
}
```

3. `src/scheduler.ts` runTask 内——主循环前建一次 `const aging: AgingOptions = { minutesPerBoost: cfg.run.agingMinutesPerBoost ?? 15, boostCap: cfg.run.agingBoostCap ?? 5 };`，两处调用点（约 L342 `let step = nextStep(db, task.name)` 与约 L418 `step = nextStep(db, task.name)`）改为 `nextStep(db, task.name, aging)`。

**测试**（`test/p2-units.test.ts` 新 describe "nextStep aging（R1-C）"，import nextStep 自 src/scheduler.js；建单用 graph.ts 的 addStep，回拨 created_at 用卡2 同款 SQL）：

- ①现状回归：不传 aging → 高分新单先于低分老单；
- ②aging 翻转：priority=2 老单回拨 60 分钟 + priority=5 新单刚建 → 传 `{minutesPerBoost:15, boostCap:5}` → 老单先（有效 2+4=6 > 5）；同场景不传 aging → 新单先（对照）；
- ③cap 封顶：priority=0 回拨 999 分钟 → 加成恰为 cap=5（有效 5），与刚建的 priority=5 新单同分 → id 小者（老单）先；
- ④关闭语义：`{minutesPerBoost:15, boostCap:0}` → 行为同 ①。

**验收**：`npm test` 全绿（再 +4）；`npx tsc --noEmit` 零输出。**不改 config.yaml**（默认值在代码）。

### 卡4 LZ-1：浏览器懒启动（纯 API step 零 chrome 生命周期 + 消灭 0KB HAR）✅274072a

**背景**：agent.ts 约 L173-177 每个 worker step 无条件 `BrowserPool.start()` 起真 Chrome + 建 BrowserSession（挂 HAR 路径）；纯 API 任务下 7 个 step 白起白杀 7 个 Chrome、落 7 个 0KB HAR（任务档 P-3/V5）。**状态载体不受影响**：cookie/浏览器状态在磁盘 profile（`taskDir/.at1/chrome-profile`），Chrome 进程本就每 step 杀旧拉新，懒启动只推迟拉起时点。

**落点与改动**：

1. `src/tools/browser.ts`——BrowserSession 三处：

- 构造第一参 `endpoint: string` 改为 provider：`connect: () => Promise<string>`（唯一构造方是 agent.ts，直接改签名）；
- 加私有标记 `private everConnected = false;`；page() 的连接分支改为：

```ts
if (!this.browser) {
	const endpoint = await this.connect();
	this.browser = await chromium.connectOverCDP(endpoint);
	this.everConnected = true;
}
```

- dispose() 的 flush 条件改为 `if (this.harPath && this.everConnected)`——**从未起过浏览器不落盘（0KB HAR 消灭在此）**；其余（detach/close/置空）不变。

2. `src/agent.ts`——约 L163-177 与 finally（约 L272-273）：

```ts
// LZ-1 懒启动：浏览器工具首次调用才起 Chrome——纯 API step（全程 Bash/curl）零 chrome 生命周期、零 0KB HAR。
// 状态不受影响：profile 目录（taskDir/.at1/chrome-profile）在磁盘上，起不起进程都在那。
const poolRef: { pool?: BrowserPool } = {};
let browserSession: BrowserSession | undefined;
```

try 块内（原 `if (opts.browser !== false)` 整段替换）：

```ts
if (opts.browser !== false) {
	const harPath = join(taskDir, "evidence", "traffic", "har", `${sessionId}.har`);
	browserSession = new BrowserSession(async () => {
		poolRef.pool ??= await BrowserPool.start(taskDir);
		return poolRef.pool.endpoint;
	}, harPath);
}
```

finally（顺序保持：先 dispose 断连+flush，再杀 Chrome）：

```ts
if (browserSession) await browserSession.dispose();
if (poolRef.pool) await poolRef.pool.shutdown();
```

原 `let pool: BrowserPool | undefined;` 声明删除。`opts.browser === false`（P3-10 降级）路径不变。

**测试**（`test/browser-pool.test.ts` 新 describe，vi 替身风格照同文件）：

**验收**：`npm test` 全绿（再 +1）；`npx tsc --noEmit` 零输出。真机验证（留给续跑观察，不在本卡）：纯 API step 后无 chrome 进程残留、`evidence/traffic/har/` 无新增 0KB 文件。
