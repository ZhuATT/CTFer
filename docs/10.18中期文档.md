# AT1 v4 架构文档（2026-10-18 · P2fix 后系统现状）

> **本文是 v4 的系统架构说明书**：系统是什么、由什么组成、每个部件怎么工作、为什么这样设计。过程性记录（施工/验收/坑）不入本文，见文末指针。

## 1. 系统定位与设计哲学

AT1 是一个**自动化渗透测试框架**：给定一个授权目标（scope）和一个可判定的目标（goal），系统自主完成"规划 → 执行 → 再规划"的循环，直到目标被证明达成、或方向探尽正式收尾、或预算耗尽。产出是一张带证据血缘的图（facts / findings / 证据文件），而不是一份自由文本报告。

五条根设计理念，所有组件都从它们推导：

| # | 理念 | 推导出的东西 |
|---|---|---|
| 1 | **图是唯一真相，磁盘即进度** | 全部状态在 SQLite + task 目录；进程随时可杀可续；无常驻内存状态 |
| 2 | **调度权集中，执行权分离** | planner 是唯一派单者；worker 只做领到的一条 step；人不直接命令 worker |
| 3 | **微内核**：pi 只当循环机器 | 选 pi-agent-core + pi-ai（L1），不用 SDK/CLI 层；一切行为由我们自己的工具面 + prompt + guard 决定 |
| 4 | **程序兜底优先于 prompt 纪律** | 拒重、收尾防线、空气证据校验、不报表清单全在代码层；prompt 只负责判断，不负责把关 |
| 5 | **现象不是漏洞** | noreport 检察官在进件口拦截"形状即现象"的上报（CORS/指纹/sourcemap…），实害豁免先行 |

与 v3（legacy-python，已归档）的结构差异：v3 是 driver + worker + 观察者三角（worker 写盘、观察者翻译入图）；v4 收敛为**调度器 + planner + worker**，图写入从"观察者事后翻译"变为"角色经工具直写、程序即席校验"——少一个角色，少一次翻译损耗，多一层程序把关。

## 2. 总体架构

### 2.1 进程与组件

整个系统是**一个 Node 进程**。三类 LLM 会话（planner / worker）以库调用形式跑在本进程内（pi Agent 对象），不是子进程。

```
node dist/index.js run <task> [--step-timeout-min N] [--max-rounds N]
│
├─ 调度器 runTask（scheduler.ts，常驻，自身零 token）
│   ├─ 启动：run.lock 抢锁 → 清扫 running 尸体 → initTask（幂等 + standards 快照）
│   ├─ watcher（1.5s tick，双信号源）：
│   │    control/stop   → 置停 + abort 当前会话（优雅收尾，秒级急停）
│   │    steer.jsonl    → 新行且目标在跑 → agent.steer() 送达
│   └─ 主循环：终止检查 → hints 收割 → （有事件或无 open 时）唤醒 planner
│              → worker 领一条 step 执行 → 事件累积 → 下轮
│
├─ planner 会话（每次唤醒新建，用完即弃）
│   工具：add_step / conclude_task / prove_goal / TodoWrite / list_facts / node_detail
│   输入：事件 delta + 全图态势 + 跨唤醒待办 [+ 收官判定变体]
│
├─ worker 会话（每条 step 一个）
│   工具：Bash / Read / Write / browser_navigate / browser_snapshot / submit_fact / submit_finding
│   约束：guard（beforeToolCall 拦截）+ 血缘态势（只见与自己相关的图）
│
├─ browser-pool：detached Chrome（CDP），与进程仅记账关系（.at1/browser.json）
│
└─ 磁盘：SQLite graph.db + task 目录（evidence/ standards/ control/ todos.json）
```

### 2.2 一次 run 的时序

```
runTask(task):
  抢锁（活锁→拒双开报 pid；死锁→接管）           ← 互斥保证单实例
  清扫 running→exhausted                          ← 上次异常退出的尸体标记
  initTask（幂等：goal/seed step 已存在则跳过；standards/ 不存在则快照拷贝）
  启动 watcher（stop 监视 + steer 投递）
  loop:
    ① 终止检查（五触发器，见 §4.3）
    ② 收割 hints（文件偏移，防重放）
    ③ 唤醒判定：有未消费事件 或 无 open step → 唤醒 planner 消费事件
       （planner 派 0 且无 open 且 goal 未达 → planner-zero 判停）
    ④ worker 领 step（priority DESC, id ASC）→ running → 执行（超时与 stop 共用 abort 通道）
    ⑤ step 收尾（done/exhausted）→ step_done/finding 事件 → 回到 ①
  finally: 删自己的锁、关库
```

### 2.3 信任模型

| 主体 | 能写什么 | 能读什么 | 边界 |
|---|---|---|---|
| worker | 图写入**只能经 submit_fact / submit_finding**（程序校验：证据文件存在+哈希、同义幂等、noreport 预检） | 本 step 血缘态势 + standards/ + evidence/ | 模型从不直接碰 DB；guard 拦截每一笔越界工具调用 |
| planner | 图写入只能经 add_step / conclude_task / prove_goal（拒重、openCount 防线、空气证据校验） | 全图态势 + todos.json + standards/ | 纯读图无 Bash；hint 对它是建议级 |
| 操作员 | control/ 下三个信号文件（hints / steer / stop） | — | 不直接命令 worker；steer 不影响调度 |
| 调度器 | 状态翻转 + activity 记账 | — | 不产生任何内容 |

## 3. 数据模型（图与基底）

**存储**：每 task 一个 SQLite（`AT-src/tasks/<task>/graph.db`），三张表：

- `nodes`：id / kind / state / origin / session_id / step_id / priority / payload(JSON) / 时间戳
- `edges`：src / dst / rel / note
- `activity`：全量操作时间线（worker / tool / summary / detail / token 四列 / is_error）——**复盘取证的唯一权威源**

**节点四类与状态机**：

| kind | 状态机 | 谁翻转 |
|---|---|---|
| goal | `open → achieved`（prove_goal，落 proves 边）/ `open → closed`（conclude_task，**不落边**——收尾不是证明） | planner 经工具 |
| step | `open → running → done / exhausted（超时或急停）/ blocked / cancelled` | 调度器 + worker 收尾 |
| fact | 提交即 `confirmed`（带 confidence: observed/inferred） | worker 经 submit_fact |
| finding | 提交即 `reported`（等 P4 复测） | worker 经 submit_finding |

**四条边（账本）**：`dispatch`（goal→step，谁派的）/ `produces`（step→fact/finding，谁产出）/ `proves`（fact→goal/finding，证据血缘——审计"谁证明了谁"）/ `derives_from`（上游节点→新 step，派生依据）。

**核心不变式：边是账本，状态是开关。** 结束判定永远看 goal 节点状态；边提供审计血缘与 planner 的判断原料（prove_goal 的 evidence 必须是图内 fact，就是用图结构把"空气证据"挡在门外）。

## 4. 调度器（scheduler.ts）

### 4.1 生命周期与互斥

- **run.lock**（`control/run.lock`，JSON {pid, started}）：启动时校验——锁内 pid 活着（tasklist 校验镜像名 node.exe，防 PID 回收误判）→ 抛错拒双开；死了 → 覆写接管。收尾 `finally` 只删**自己持有的**锁（接管竞态保护）。
- **启动清扫**：`running → exhausted`。系统单进程，进程死 = 在跑全死，running 必是尸体。
- **续跑**：再敲 run 即续——initTask 幂等、图状态即进度、非 fresh 且图非空自动发 `resume` 触发事件；历史 stop 文件被主动清除（不会一停永停）。

### 4.2 唤醒策略（事件驱动）

planner 的唤醒条件：**本轮有未消费事件**（step_done / finding / hint / steered / resume）**或无 open step**。空事件且有 open step 时直接跑 worker 不唤醒（成本纪律）。

事件源说明：step 的唯一生产者是 planner 本人，因此**不存在"新 step 唤醒"事件**；worker 的 fact 提交发生在 step 会话内，归入 step_done 批次不单列。每次唤醒约 5k in / 3k out token（每 step 一次唤醒，成本已计入设计）。

**planner-zero 判停**：唤醒后仍无 open step、派 0、goal 未达 → 判停退出。这是"模型认为无事可做"的正常出口之一。

### 4.3 任务结束（五触发器）

| 触发器 | 语义 | 退出码 |
|---|---|---|
| prove_goal | 目标被图内 fact 实证（量化条件须核对态势实测值） | 0 |
| conclude_task | 方向探尽/目标不可达的正式收尾（防线：openCount==0 才允许——还有活干就无权宣判终局） | 0 |
| maxRounds / budget | 程序兜底 | 1 |
| control-stop | 操作员急停 | 0 |

### 4.4 停止三层

① `stop` 命令写信号文件（意图声明）→ ② watcher 1.5s tick 发现 → 对当前会话调 `agent.abort()`——与 step 超时**同一条优雅收尾路**（step 落 exhausted、已产出保留、activity 落账），秒级响应 → ③ 真僵死（abort 都不返回）才人工 `taskkill`（锁内 pid 已打印）。**不自动杀进程**。

强杀与急停的区别：急停走正常收尾（删锁、干净退出）；强杀留下死锁 + running 尸体，由下次启动的接管 + 清扫自愈。两者殊途同归都能续跑（进度全在 SQLite）。

## 5. planner

**会话形态**：每次唤醒新建 Agent（与 worker 永不同会话），用完即弃；跨唤醒记忆靠三个外部载体——图本身、`todos.json`（串行链待办）、事件 delta。通道独立配置（`config.channels.planner`）。`thinkingLevel:"low"`（glm 系列硬要求）。

**工具面六件**（全部经程序校验，回执是模型可读的纠错信息）：

| 工具 | 参数要点 | 程序校验 |
|---|---|---|
| add_step | 批量 ≤4；summary/note/priority/parent_ids | 同义拒重（归一化精确匹配，只拦 open/running；done 重派是合法自由）；parent 必须存在（derives_from 边） |
| prove_goal | goal_id / evidence_id / reason | goal 须 open；evidence 必须是图内 fact；reason 非空 |
| conclude_task | reason | **openCount==0 防线**；goal 须 open；reason 非空 |
| TodoWrite | 全量覆写 ≤20 条 | —（串行利用链载体：本轮只派前置已满足的那步） |
| list_facts | 分页 20 | — |
| node_detail | id | 采信前下钻看证据的通道 |

**prompt 结构**（字节级稳定的静态 system + 动态 user 首条，缓存友好）：

- **system（v1.2，决策流程式）**：唤醒=消化新变动 → ①读变动 ②判目标 ③判方向（重派规则/负向复核/组合扫描/路线多样性）④定产出（派/证/收尾/0 派收工/串行链）。核心纪律：note 是 worker 理解方向的唯一上下文；引用图内容=节点 id+转述，禁贴原文。
- **user 首条四节**：【任务目标】/【本次实际变动（先看这里）】（事件 delta 渲染）/【态势预取】（全图 JSON+字段导读）/【跨唤醒待办】。
- **收官判定变体**：唤醒时图上无待办 step 则追加——"三选一必答，0 派不是选项：派真方向 / prove_goal / conclude_task"。

## 6. worker

**会话形态**：每条 step 一个 Agent；user 首条 = 领到的 step（summary+note）+ 血缘态势 + standards 索引 + 完成定义。系统 prompt 六行：只做领到的一条、初次受阻≠探透、约束自检、结论必有证据、边发现边写回、完成即停——另有插话纪律句（见 §7 steer）与阴性出口（探不动也是结论，落阴性 fact 再走）。

**工具面七件**：

| 工具 | 说明 |
|---|---|
| Bash | task 目录内执行；输出 8KB 截断；超时默认 60s（上限 300s）；**curl 就绪，nmap/dig/nc 未预装**（用 curl 等价实现） |
| Read / Write | 锚定 task 目录；Read 64KB 截断；Write 建议 evidence/ 下 |
| browser_navigate / browser_snapshot | 经 BrowserSession connectOverCDP 附着池内 Chrome；快照为可访问性树文本，8KB 截断 |
| submit_fact | 一条一断言；evidence 必须是已写盘的文件（路径逃逸校验+sha256）；同义幂等返回旧 id；confidence=observed/inferred |
| submit_finding | 严门：真实触发+可复现才报；**noreport 预检前置**（reject 硬拒不入图 / suspect 放行+公诉意见）；related_fact_ids 连 proves 边 |

**guard（beforeToolCall，拦截式）**：两条规则——scope host 白名单（从命令/URL 抽 host 比对 task.scope.hosts）与破坏性命令禁令。拦截回执是"纠错+指路"型：告知违反了什么、正确做法是什么（如"范围外目标记 fact 上抛，不要动手"）。

**态势（血缘精简版）**：goal + 本 step 直产 facts（接续上下文）+ 上游 derives_from 链上所有 facts + 全图 counts——**不含全图 steps/findings 明细**（那是 planner 的视野；对"只做一条"的 worker 是成本+越界引诱）。stepLineageView 沿边遍历收集。

**浏览器（browser-pool）**：Chrome 归池管——detached 拉起（CDP 随机口）、`.at1/browser.json` 记账、探活自愈（死→杀树重拉）、收尾杀树删账。BrowserSession 只 connectOverCDP 附着、只断连不杀进程（所有权单一：会话不该拥有它没启动的东西）。

## 7. 操作员介入（四通道）

设计原则：**显式选择，不自动路由**——操作员自己知道该用哪条通道；系统不做"智能判断该给谁"的中间层。

| 通道 | 层级 | 语义 | 机制 |
|---|---|---|---|
| **hint** | 调度层 | 建议级：拨方向/给情报/给禁令，影响**未来的 step**；planner 可采纳/忽略 | `hint <task> "文本"` → hints.jsonl → 轮收割 → 渲染进 planner 事件组；时效=当前 step 跑完的下一次唤醒 |
| **steer** | 执行层 | 对**在跑的 step** 补情报/纠偏；不影响调度、不派活 | `steer <task> [--step N] "文本"`（无在跑 step 拒发）→ steer.jsonl → watcher 秒级 `agent.steer()`；worker 的插话纪律="不是新任务，完成当前 step，相关观察落 fact"；`steered` 事件同步进 planner（防盲区） |
| **stop** | 全局 | 急停（§4.4 三层） | `stop <task>` |
| **reopen** | 目标层 | 换新 goal、原图续跑（历史 facts = 新 goal 的先验），发 goal_changed 触发 | 预留（M5 UI / P3 CLI） |

hint 与 steer 的边界一句话：**hint 改变接下来做什么，steer 改变现在正在做的这件事。**

## 8. 模型通道（pi L1 微内核）

**选型**：`@earendil-works/pi-agent-core`（Agent 循环、abort/steer 原生）+ `@earendil-works/pi-ai`（streamSimple、Model 对象、多 provider 适配）。不用 pi 的 SDK 层（太重，默认行为黑盒多）也不用 CLI 子进程（自主工具面是 guard 的敌人）——**选最薄的层 = 可控变量最少**。pi 没有的（skills/sessions/MCP）按需自建，已有 standards 机制即是。

**隔离**：baseUrl 钉在 Model 对象上、apiKey 经 `getApiKey` 显式传——pi-ai 的请求路径不读 ANTHROPIC_BASE_URL，机器全局 env 永远够不着本框架的通道。对 pi 的依赖面只有两个接口（streamFn + tools 注册），未来换自写循环替换面是一个函数。

**config.yaml**（`AT-src/config.yaml`，手写两层缩进栈式解析）：

```yaml
channels:
  worker:  { model: glm-5.3, api: anthropic, keyEnv: AT1_API_KEY }   # api: anthropic|openai
  planner: { model: glm-5.3, api: anthropic, keyEnv: AT1_API_KEY }   # baseUrl 内置映射可覆写
run: { maxRounds: 20, budgetMs: 3600000 }
```

worker / planner 各自独立通道配置——为模型对照实验留口（实测：429 余额耗尽时改一行 yaml 切换端点，零代码改动）。key 永远走环境变量名引用（keyEnv），值在 `.secrets.env`（gitignore）。

**已知模型坑位**：glm-5.3 拒 `thinking:disabled`（错误码 1210），必须 `thinkingLevel:"low"`。

## 9. 参考资料机制（standards/）

**`<task>/standards/` = agent 参考资料唯一目录**。initTask 时从仓库根 `src标准/`（五家 SRC 厂商的漏洞评级细则）快照拷贝；已存在则跳过（历史任务保持创建时版本）。未来 skills 手册等同入此目录。

**渐进披露**（复刻 skill 的"只加载 description"）：`standards/INDEX.md` 每册一行（文件名+一句话描述），注入 worker 的 user 首条（几行固定开销）；正文按需 Read/Grep（用一次付一次）。引导行挂**触发条件**不挂"必读"：

- submit_finding："severity 定级拿不准时，Read `standards/<目标厂商>.txt` 查评级细则（Grep 关键节，不全量读）"
- 开工句："按 step 方向查阅 standards/ 相关手册，有则先读相关节，没有就跳过"

## 10. 关键设计决策（为什么是这样）

| 决策 | 内容 | 依据 |
|---|---|---|
| 单 worker | 本大阶段不做并发；停/断/续做扎实 | 砍的是并发机械，留的是语义正确性 |
| 事件驱动唤醒 | 每有新战况即唤醒 planner（方案 C） | ARTEX 原版语义；单 worker 下成本 +30% 已知情接受 |
| prompt v1.2 决策流程式 | 与唤醒机制配对改写 | 教训：把 A 机制的 prompt 文本移植到 B 机制上 = 死文字+自相矛盾 |
| conclude 防线 openCount==0 | 还有活干就无权宣判终局 | Cairn/ARTEX 均不给模型无条件弃守权；弃赛是预算的事不是模型的判断 |
| 不上目标分解器 | 大目标由 planner 用 step 边探边分解（延迟/自适应） | 模糊 goal 下分解器只能发明量化代理=虚假精度；真实测法取决于踩点后的地形 |
| dispatch 边保留 | 单 planner 单 goal 下仅审计价值 | 成本≈0；多 goal/多 planner 一来立刻有用 |
| steer 独立通道 | 不做 hint 升级、不自动路由 | 时效需求（step ~分钟级）与调度权威（planner 唯一派单）两全 |
| noreport 检察官 | reject/suspect/pass 三态 + 实害豁免先行 | 绝对不报铁律的程序化；"现象是载体时改报实际影响"给出路 |
| 拒重精确匹配 | 归一化相等，不做语义相似 | 保险丝定位：误伤阻断正活不可接受，漏放交 prompt 第二道 |

**参考系**（借了什么/没借什么）：ARTEX——事件驱动唤醒、planner prompt 骨架、wrapup 哲学；没借目标分解器、kill_work/steer_work（多 worker 世界）、Bash 开局探测（seed step 替代）。Cairn——单 goal + 证明制收官、状态空间搜索哲学；没借容器化执行。pi——Agent 循环、steer/abort 原生能力；没借 L2 全家桶。

## 11. 系统参数（锁定值）

| 参数 | 值 | 出处 |
|---|---|---|
| worker step 超时 | 6min（CLI `--step-timeout-min` 可覆写） | 真机校准 |
| planner 会话超时 | 5min | 默认 |
| maxRounds / budget | 20 轮 / 1h（config 可覆写；CLI 可临时覆写） | config.yaml |
| watcher tick | 1.5s（测试可调小） | 秒级急停与开销平衡 |
| add_step 纪律 | 批量 ≤4；组合扫描每轮 ≤2 | prompt v1.2 |
| 态势预取 | planner=全图（steps 全量+recent_facts 20+counts）；worker=血缘+standards 索引 | 分角色视野 |
| hints / steers | 单条 500 / 1000 字截断；文件偏移防重放；steer 无在跑 step 拒发 | 通道协议 |
| Bash | 超时 60s（上限 300s）；输出 8KB 截断 | 工具面 |
| 浏览器 | CDP 探活 2s；启动 deadline 20s；换口重试 3 | browser-pool |
