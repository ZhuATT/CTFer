## 3. Guard：已同意的施工范围与边界

### 3.1 回执（已同意文本）

保留现有平台管控框架，正确做法替换为：

> 移除命令中的删除操作；需要独立临时文件时使用新的唯一文件名，保留已有文件。不得换用其他方式执行同一删除操作。

不提供 evidence/ 自有目录删除豁免，不教模型用覆盖或其它解释器替代删除。

### 3.2 匹配输入

破坏性规则检查真实 `args.command`，不能检查 JSON.stringify 后的 digest；digest仅保留作原有审计。Bash参数不是字符串时安全拒绝，不执行String(object)兜底，不让guard异常逃出。

静态预检不是shell解析器或沙箱；不引入AST、外部依赖，不承诺识别任意脚本/子进程。

### 3.3 本批精确覆盖边界

- 删除：在现有禁令基础上补普通直接rm、rm -f/-r/-rf/--recursive、rmdir、unlink；真实空格/制表/换行均测试。保留mkfs/dd/format/停服原规则。不是通用解释器行为检测。
- 保守策略：仅展示/注释/引号内出现上述危险文本也可能拒绝，写回测试与文档；本批不建设“纯文本例外”，不为降低误拦放松删除政策。普通echo/grep/mkdir等无危险片段命令应继续通过。
- URL：从Bash原始命令提取显式http(s)候选，或直接解析browser_navigate.url；协议大小写兼容，用标准URL取hostname，统一小写并与scope精确匹配，端口不算host的一部分。
- 带用户信息的URL必须取@后的真实host；相似前缀域名不能通过。IPv6用URL解析并对地址的外围方括号作一致归一化，不做DNS解析。
- browser_navigate的非法/非http(s)URL拒绝；Bash出现显式http(s)候选但解析失败则拒绝并说明“URL无法校验scope”，不静默丢掉。scope的Set热扩权引用语义保持不变。
- 不恢复裸域名猜测；模板字符串、引号中的URL可能保守误拦。重定向/动态地址/DNS最终目的地约束留P4，不宣称本批完成网络隔离。

### 3.4 最小审计（复用activity，不迁移表）

guard选项加stepId，使用activity.node_id；call和blocked的JSON detail带toolCallId，blocked带ruleId及完整平台回执。保留summary='call'与'blocked: …'查询口径，不因增加字段改变统计类别。

agent订阅tool_execution_end记kind=result、tool原名、summary='tool success'或'tool error'、is_error；detail只含toolCallId/isError，不复制正常正文或错误正文。工具事件isError不表示shell exit一定为0，不能伪称Bash业务成功。

不新增完整命令/凭据副本；现有call参数留存策略本批不重构。新结果日志不写Cookie/token或任意工具输出，既能统计Read/submit错误又不需要通用脱敏引擎。

### 3.5 独立挂账：证据不可变

当前 Write 可覆盖已有文件，“禁止删除”不等于“保护历史证据”。未来考虑按已引用证据与工作文件分层保护；本批不动文件可写策略，不能一刀切禁止临时 cookie 罐更新。

## 4. 最小计时与 abort

### 4.1 字段与边界

只加queue_wait_ms、worker_elapsed_ms、cleanup_elapsed_ms；UTC开始/返回/清理结束时间供对账。queue_wait=worker入口UTC减created_at（负数钳0，包含停机时长，不是纯忙碌等待）；worker_elapsed=函数入口到prompt返回/抛错；cleanup_elapsed=finally资源清理起止。后两者用单调时钟。

计时放既有会话结果JSON detail，不新增独立计时表或初始化细分指标。构造失败没有完整worker结果时，scheduler兜底blocked允许计时缺失，不能编造0耗时成功。旧数据无新字段就注明unknown，不回填假精度。

### 4.2 取消原因

首次生效的本地取消记step-timeout或operator-stop，后来的provider-aborted不能覆盖。无本地信号而消息stopReason=aborted，记incomplete/provider-aborted，不假设已证实网络断线。

入口/发请求前signal已aborted必须退出，不发新模型请求。prompt返回进入finally时先撤销计时器及外部监听，清理慢不能误记模型执行超时。

保持合作式取消与资源清理，不硬杀工具进程；Bash未消费外部signal的边界登记但不扩改。本地取消与error同时存在仍保留双方诊断，本批状态沿用本地取消优先的exhausted语义。

## 5. 完成判定：本批最低交付门

### 5.1 问题样本

| step | 工具调用尝试 | 新 fact/finding | 观察 |
|---|---:|---:|---|
| #22 | 0 | 0 | 1轮、最终文本空、usage为0 |
| #3 | 6 | 0 | 有动作但无结论写回 |
| #53 | 4 | 0 | 最后非空文本仍在描述下一步 |
| #62 | 12 | 0 | 最后非空文本仍在描述下一步 |
| #64 | 0 | 0 | 1轮、最终文本空、usage为0 |

这些并非已证同因；没有原始 stopReason，不能都归为中转断流。现逻辑仅以本地 aborted/transportError 判断，剩余皆 done。另有一处风险：texts 数组只保留非空文本，因此“最后非空文本”不一定是最后一条 assistant 消息。

### 5.2 incomplete 谁标记？

**已拍板：程序标记，agent 收尾产出唯一权威结果，scheduler 消费同一结果，不再用 aborted/transportError 自行重算。** worker 只提交事实/结论；planner 消费状态、判断是否续接，不负责发现基本的空结束。

否则仅 agent 增 incomplete、scheduler 仍沿用三元表达式，会出现库中 incomplete、planner 事件却写 done 的分裂。

### 5.3 唯一判定表（按顺序匹配）

| 顺序 | 条件 | outcome / reason |
|---|---|---|
| 1 | 本地取消生效 | exhausted / step-timeout或operator-stop |
| 2 | 检测到既有通道error，或构造/执行抛错 | blocked / channel-error或worker-error（无result的兜底归scheduler） |
| 3 | 无本地取消，最终stopReason=aborted | incomplete / provider-aborted |
| 4 | 最终stopReason=length | incomplete / output-length |
| 5 | 无最终assistant消息、stopReason缺失或不是正常stop | incomplete / missing-final-message或unexpected-stop |
| 6 | 正常stop，但本会话无成功提交回执 | incomplete / no-delivery |
| 7 | 正常stop，且本会话至少一条合法交付 | done / delivered |

局部长度截断若pi随后正常继续并结束，不因历史length永久判失败；最终length必须未完成。通道error沿用已有检测，不因已有fact抹掉。最终文本空但正常stop且已有合法交付允许done：空文本不是独立故障证据；finalText必须为最后消息的文本，不能回填前面的“接下来准备”。

done只证明最低交付，不证明派单全部答完，也不保证事实正确。已有部分产出遇异常保留产出，异常状态不变。

### 5.4 不做同上下文“补交一次”（已拍板）

**取消同会话自动补交**，不增加 finishTurn/额外 prompt 请求强迫补交，也不机械重放网络动作。需继续时由 planner 派新 step；不是每张 incomplete 无条件重派。

补充判断：脚本通过 pi 结束钩子发提醒在技术上可行，但不能保证上游可用或模型不补造结论；额外一次请求也不是必要闭环。取消它是工程范围与风险取舍，不是“脚本绝对做不到”。

新接续单只补未完成项，引用已有产出；不能从头重跑所有动作，更不能因为没发现而扩展权限。

### 5.5 交付检测不能只数新增节点

- 记录成功 submit 回执，包括 dedup 返回已有 ID；不能把 guard 的调用尝试当提交成功。
- 校验回执属于当前 task、当前 step；不能靠把提交挂错 step 来满足交付门。
- 同 task 旧 fact 被返回，只能证明一次合法提交成功，不自动证明本次派单完成。
- 零 usage 不是失败的充分条件；有一条 fact 也不是“任务全部完成”的充分条件。
- 本批不增加“合理跳过”工具或强迫造fact：没有新交付就如实incomplete，planner可基于已有事实决定无需补派。

## 6. Planner接续：复用现有机制，不增生命周期协议

程序检查运行信号与最低交付；planner检查是否答完原step。需继续时通过已有add_step派新单，parent_ids指原step，note转述已有结果与缺口。原step保留incomplete，不改成open重跑。

已被其他事实覆盖或当前不值得继续时，planner可以解释理由不派单；本批不加covered/defer状态、resolve_step工具或持久处置协议，不宣称每条未完成方向都会被可靠解决。若done仅回答部分要求，planner也可依据缺口派补充单，prompt不能把done当充分性保证。

### 6.1 结果最小持久化与可见性

每个step只增加可选last_execution元数据：session_id/outcome/reason/stop_reason、delivery_refs（kind/id/dedup）、timing。不加attempt号、重试次数或decision；旧step没有该字段则显示unknown。既有activity.result保留完整本次结构化摘要；step只存最新摘要，供node_detail/graphOverview/resume读，不复制完整工具输出。

StepPayload及graph内部类型需保留字段，防zod strip；planner创建step不能伪造last_execution，addStep应只接受原派单字段。summary/note等旧内容保留，不全量重写payload。

scheduler收到result时直接使用其outcome；无result抛错仍按worker-error兜底blocked并留安全摘要。新reason/交付引用须结构化进入trigger，不能被400字符finalText截断。

### 6.2 保险丝保持小范围

明确blocked按原阈值累计并熔断；done清零；incomplete与非通道取消不当“通道修复成功”清零，亦不增加blocked计数。planner唤醒成功仍不能清零。

不加第二套未交付阈值、血缘重试预算、人工解锁或跨run计数；依靠原max-rounds/budget限制单run投入。它们不是严格墙钟截止，也不是跨run防重复保证。若实跑证实反复补派，再依据样本单独设计。

### 6.3 不增加planner证据工具

现有node_detail只读payload和证据路径。本批只改善交付摘要与异常可见性，不新增任意文件读取或证据窗口工具，不宣称自动验证fact内容。事实/证据语义充分性仍由planner按现有能力研判，证据正文消费缺口单独挂账。
